# ADR-0002: イベントキューは単一の DB テーブルで持つ

- Status: Accepted
- Date: 2026-06-22（UC-6 を受付→確定のサーガに見直した際の決定）

## Context

複数集約をまたぐユースケース（UC-6 注文確定）は弱整合で進め、workflow が非同期にオーケストレーションする。そのためにイベントの受け渡し手段が必要になった。候補は次の 3 つ。

1. feature ごとにイベント用の一時テーブルを作る
2. 外部キュー（SQS 等）を導入する
3. 単一の DB テーブルを全ワークフローで共有する

## Decision

単一テーブル `app.event_queue`（id, event_type, payload, created_at）を全ワークフローで共有する。

- workflow が polling して `event_type` で振り分ける。OTP のワーカープロセスと相性が良い
- イベントは必ず集約の状態変化とセットで発行し、`event_queue` への INSERT が状態変化の記録を兼ねる

理由:

- テーブルが一つで済み、feature が増えてもスキーマが増殖しない
- スケールアウトしても構造が変わらない
- レコードが残る限りリトライが自然に機能する（外部キューのような可視性タイムアウト管理が不要）
- 決済モックの現フェーズで外部キューはオーバーキル（YAGNI）

## Consequences

- workflow は polling ベースになる（push 通知ではない）
- **再検討の条件**: スループットが上がり polling のレイテンシ・DB 負荷が問題になったら、外部キュー（SQS 等）への移行を別 ADR として検討する。イベントの発行箇所が `event_queue` INSERT に集約されているため、移行時の変更範囲は adaptor 層に閉じる
