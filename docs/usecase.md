# ユースケース記述

`requirements.md` のユーザーストーリーを、基本フロー・例外フロー・事後条件まで具体化したもの。

## 設計上の前提（在庫・決済）

`erd.md` / `schema.hcl` の設計に基づく。実装はこの前提に従う。

- **在庫はカラムで持たない**。`products` に `stock` カラムは無く、`stock_movements`（`delta`, `type`）の `SUM(delta)` で動的に集計する（`aggregates.md` / `query_computation.md`）。
  - 入荷・初期在庫 = 正の `delta`、注文・出庫 = 負の `delta`
- **決済はモック**。注文確定時に `payments` レコードを作成して「決済済み」とみなす（外部決済は繋がない）。

## UC-1 商品を登録する（管理者）

| 項目 | 内容 |
|---|---|
| アクター | 管理者 |
| 事前条件 | 管理者として認証済み |
| 事後条件 | 商品が登録され、初期在庫が `stock_movements` に記録される |

**基本フロー**

1. 管理者が商品（名前・価格・在庫数・説明）を入力する
2. システムが入力を検証する（価格上限 100,000 など）
3. `products` に商品を登録する
4. 初期在庫数を `stock_movements`（正の `delta`, type=`initial`）に記録する
5. 登録した商品を返す

**例外フロー**

- 2 で検証エラー → エラー一覧を返す（全エラーを収集）
- 3/4 で保存失敗 → エラーを返す

## UC-2 商品一覧を見る（顧客）

| 項目 | 内容 |
|---|---|
| アクター | 顧客 |
| 事前条件 | なし（一覧は誰でも見られる） |
| 事後条件 | 在庫数を含む商品一覧が返る |

**基本フロー**

1. 顧客が商品一覧を要求する
2. システムが `products` を取得し、各商品の在庫を `SUM(stock_movements.delta)` で算出する
3. 在庫数を含む一覧を返す

## UC-3 商品をカートに追加する（顧客）

| 項目 | 内容 |
|---|---|
| アクター | 顧客 |
| 事前条件 | 認証済み |
| 事後条件 | カートに商品が追加される |

**基本フロー**

1. 顧客が商品 ID と数量を指定する
2. システムが現在在庫を算出する
3. 在庫が数量以上であればカートに追加する

**例外フロー**

- 在庫が 0 → エラー（在庫なし）
- 数量 > 在庫 → エラー（在庫不足）
- 同じ商品が既にカートにある → エラー（重複）
- 商品が存在しない → 404

| 事前条件 | 認証済み・対象のカートアイテムが存在する |
| 事後条件 | カートアイテムの数量が更新される |

**基本フロー**

1. 顧客がカートアイテム ID と新しい数量を指定する

- 数量 > 在庫 → エラー（在庫不足）

## UC-6 注文を確定する（顧客）

| 項目 | 内容 |
|---|---|
| アクター | 顧客 |
| 事前条件 | 認証済み・カートに 1 件以上の商品がある |
| 事後条件 | 注文が作成され、在庫が減り、決済（モック）が記録され、カートが空になる |

**基本フロー**

1. 顧客が注文確定を要求する
2. システムがカート内容を取得する
3. 各商品の現在在庫を算出し、注文数を満たすか検証する
4. `orders` / `order_items` を作成する（`unit_price` は注文時点の価格をスナップショット）
5. 各商品の出庫を `stock_movements`（負の `delta`, type=`order`）に記録する
6. モック決済として `payments` レコードを作成する
7. カートを空にする
8. 作成した注文を返す

**例外フロー**

- カートが空 → 409
- いずれかの商品で 数量 > 在庫 → 409（在庫不足）
- 4〜7 のいずれかで失敗 → エラー（複数集約をまたぐため、本来は補償アクションを検討する → `workflow.md`）
