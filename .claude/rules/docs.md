# ドキュメント記述の方針

## ユースケース記述（`docs/usecase.md`）

`requirements.md` のユーザーストーリーを「誰が・何を・どうするか」という**振る舞い**に具体化する。

### ドメイン言語（ユビキタス言語）で書く

実装者以外も読む前提。ドメインの言葉で書き、実装の詳細を持ち込まない。

| 持ち込まない（実装の領域） | 代わりに書く（振る舞い） |
|---|---|
| テーブル名・カラム名（`stock_movements`, `delta`） | エンティティ名（「在庫変動として記録される」） |
| SQL・集計ロジック（`SUM`, `JOIN`） | 振る舞い（「在庫を確認する」「在庫が減る」） |
| HTTP ステータス（404 / 409） | 結果の意味（「商品が存在しない」「在庫が足りない」） |

- データ構造は `erd.md`、API は `openapi.yaml`、ステータスコードはシーケンス図の領域。ユースケースから参照させる
- 先頭に**用語集（ユビキタス言語）**を置き、ドメインの語彙を定義する

### 構成

各ユースケースは アクター / 事前条件 / 事後条件 / 基本フロー / 例外フロー で書く。
UC 番号（UC-1 …）は `usecase.puml` と `todo` テストに対応させ、追跡できるようにする。

### あるべき仕様だけを書く

実装ステータス（抜け・TODO・既知のバグ）は混ぜない。未達は `todo` テストで可視化する（`testing.md`）。
※ ドキュメント全般の編集ルールは `CLAUDE.md`「ドキュメントの編集ルール」を参照。

### 定期的に見直す

ドキュメントは放置すると腐る。`requirements.md` / `openapi.yaml` / `schema.hcl` を変えたら、対応するユースケースの整合（用語のズレ・実装詳細の混入・未反映の振る舞い）を見直す。

## ロバストネス図

### 各要素の役割

| 要素 | 役割 | 名前の形式 |
|------|------|-----------|
| boundary | アクターが触るインターフェース | 「〜する」（例: 予約をキャンセルする） |
| control | ビジネスロジック・条件チェック | 「〜する」（例: 予約の存在と所有権を確認する） |
| entity | データオブジェクト | 名詞のみ（例: Reservation） |

### 書かないこと

- **HTTP エンドポイントパス** — `DELETE /reservations/{id}` は OpenAPI の領域
- **カラム詳細** — `(id, member_id, lesson_id)` は ER 図の領域
- **エラーレスポンス** — 401 / 403 / 404 などはシーケンス図の領域
- **認証方式の詳細** — Cookie / セッション / 外部認証基盤 / 管理画面ログイン などの実装は書かない。差し替え可能にするため、抽象的な「認証する」までに留める（下記参照）

### control の省略

boundary と control が同じ意味になるなら control は不要。

```
# 冗長（避ける）
boundary "予約をキャンセルする" --> control "キャンセルを実行する"

# シンプルで十分な場合は boundary → entity を直結する
```

### 詳細なケースはテストで管理

条件分岐ごとのエラーケースは robustness 図に書かず、`todo` 付きテストとして管理する。

```gleam
pub fn cancel_not_own_reservation_test() {
  todo
  // 他会員の予約 → 403
}
```

### 認証・認可は関心として描く（ただし差し替え可能に）

認証・認可は図に含める。ただし**認証方式に依存しない**よう、抽象的な一つの control で表す。

- 認証は `認証する` または `会員を解決する` という **1 つの control** に集約する
- その実装（Cookie セッション・外部認証基盤・管理画面ログイン）は図に書かない＝**差し替え可能**にする
- requirements では顧客は外部認証基盤、管理者は管理画面と方式が異なる。図を方式に縛らないことで、両者を同じ `認証する` で表現でき、後から方式を入れ替えても図が壊れない

```
# 認証が前提のユースケース
boundary "注文を確定する" --> control "認証する" --> control "注文を作成する" --> entity Order
```

実装上も同じ思想で、認証はアダプター関数（例: `fn(Request) -> Result(MemberId, _)`）として注入し、方式を差し替えられるようにする（`architecture.md` の依存性注入）。

未認証・認可エラー（401 / 403）の分岐は図に描かず `todo` テストで管理する。
